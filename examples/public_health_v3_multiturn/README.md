`dialogues.jsonl` 由 `scripts/build_multiturn_set.py` 生成，对话内容和挑选理由都写在脚本里。不带参数运行时只核对，内容不同即报错；`tests/test_multiturn_eval.py` 在 CI 中做同样的核对。字段：`follow_up` 为追问，`history` 为第一轮问题与固定下来的回答，`source_question` 为源查询原文（评测里的上限参照），`gold_evidence_ids`、`bucket`、`split` 继承自源查询，`topic_terms` 为第一轮点明的话题词。

## 构造方法

1. 追问补全后就是一条已标注的 v3 或 v3-ext 查询，所以正确片段、类别和划分都继承自它，不重新标注。test 对话只从 test 源查询构造，dev 只从 dev 源查询构造。
2. 挑选：在源查询里人工挑出问题中有明确话题词（病名、物品、地名）、能换成代词或省略的；话题没有出现在问题里的不选。
3. 第一轮问题与追问手写在脚本里。构造时检查：第一轮至少包含一个话题词，追问不包含任何话题词，追问不等于源查询。
4. 第一轮回答固定下来，评测才能复现：话题在语料里时，取该话题页面中第一段不属于源查询正确片段的原文，代表上一轮交付的一段摘录，不泄露本轮答案；话题不在语料里（语料未覆盖、超出范围），或该页面只有正确片段（`public_q11`、`public_q04` 两条）时，记为拒答。
5. 对全部第一轮问题和追问运行与应用相同的泄露检查（片段的来源字段不含对话编号，原文不含问题全文），没有命中。

## 局限（请随结果一起引用）

- 对话由 AI 撰写，只有一位复核人，没有医学专家审核，不代表真实用户的多轮对话。都是两轮，指代对象都在上一轮问题里明确出现，没有跨多轮、指代多个对象或话题转换的情况。
- 第一轮问题常用规范病名（例如“疟疾”），而源查询可能是口语（“打摆子”），补全后的问题可能比源查询更容易检索，所以“补全”条件可以超过以源查询为准的上限参照。
- 第一轮回答是按规则选的一段原文，不是系统实际的回答；它只影响问题补全条件，不进入检索和生成。
- test 不可回答的对话只有 20 条，0 误答对应的 95% 区间上限约为 16%。
- 语料来源与使用限制见 [v3 语料说明](../public_health_v3/README.md)。
